1. Project Overview

TantuLink, branded in the UI as Taana, is a multilingual voice-and-text marketplace demo connecting rural Indian craft producers with buyers. The current code is strongly centered on handloom/textile examples while the onboarding and visible terminology have been expanded to use Artisan/Producer language in selected areas.

Target users: an Artisan/Producer experience, a Buyer marketplace experience, and a hidden/internal Admin experience. A separate Verifier product or role is not implemented.

Architecture: React 19 client rendered by Vite, an Express server written in TypeScript, server-side in-memory seeded products/orders/transactions, client React state, localStorage caches, a service worker, offline outbox synchronization, and REST-style API endpoints. The database layer is represented by interfaces and SQL DDL in src/db/schema.ts, but no database driver or live database connection is present in the inspected code.

Technologies: React, TypeScript, Vite, Tailwind CSS v4 Vite plugin, Express, Motion, Lucide icons, Google Gemini package dependency, Web Speech API, Web Audio API, service worker APIs, and Unsplash image URLs. The pricing server route is implemented in server.ts; the inspected code does not establish a live external Gemini call for the pricing route.

2. Application Flow

  1. Open: src/main.tsx registers /service-worker.js and renders App.tsx.
  2. Initial state: App.tsx reads taana_onboarding_done, taana_profile, cached products, cached orders, offline state, and URL query parameters.
  3. Onboarding: when onboarding is incomplete, OnboardingFlow.tsx presents language, account type, and dynamic profile forms.
  4. Experience routing: completed profiles are normalized to the legacy client roles weaver, buyer, or admin. App renders WeaverView, BuyerView, or AdminDashboard.
  5. Marketplace: Buyer browses seeded/local products, opens details, checkout, orders, payment protection, and disputes.
  6. Artisan: Artisan/legacy Weaver view lists products, uses the product wizard, sees incoming orders, QC, earnings, GI details, pricing, disputes, and payment protection.
  7. Admin: Admin mode exposes GI, dispute, and transaction tabs. The current URL query parameter ?role=admin is accepted by the client.

4. Buyer Experience

  • Marketplace: BuyerView.tsx lists available products and supports saved items.
  • Search: conversational query parsing supports color, budget, material, occasion, and related filters via parseConversationalSearch in data.ts.
  • Product details: images, price, origin/region, artisan story, specifications, dimensions, material, care instructions, GI status, and “Buy Right” review checkbox.
  • Recommendations: a same-craft-family panel exists in product detail. It derives families from product title/material/description/GI category and shows a localized empty message when no same-family products exist.
  • Saved/recent items: saved product IDs, recently viewed IDs, and search history use localStorage.
  • Checkout: direct checkout shows product recap, price breakdown, logistics, platform fee, artisan direct amount, and simulated UPI completion.
  • Orders: order tracking, status progression, payment protection, dispute area, and post-delivery issue reporting.
  • Voice: voice search and story narration through VoiceHelper.tsx.
  • Profile: AccountModal.tsx shows identity, receipts, cached order archive, data saver, and offline payment QR simulation.

Cart: no multi-item cart state or cart endpoint was found. The current flow is product selection followed by direct checkout.

5. Artisan Experience

  • Dashboard: earnings, active orders, monthly sales visualization, listed products, success tips, and connection status.
  • Product creation: photo/template selection, guided Q&A, voice or typing input, review, publish, GI draft data, and AI pricing review.
  • Product management: current products show price, listing status, GI badge, and GI modal access. Product edits beyond the wizard are limited/not comprehensively implemented.
  • Orders: incoming orders, tracking, QC checklist, dispute response, and payment protection.
  • Earnings: demo available/pending earnings and completed order statistics.
  • GI: GI information can be entered during listing; status is locally represented as pending in the created product. The dedicated server GI submission route exists but is not called by the wizard.
  • AI pricing: AiDynamicPricingModal.tsx sends pricing inputs to the server endpoint and has a deterministic client fallback.
  • Voice: guided question narration, speech recognition/simulation, and speech synthesis.
  • Notifications: visible success/error/status banners and toast-style feedback exist; no separate notification service or persisted notification entity was found.

6. Product Categories

Onboarding currently lists these producer craft categories:

Handloom & Textiles; Pottery & Ceramics; Woodcraft; Metalcraft; Jewellery; Leathercraft; Bamboo & Cane; Embroidery; Folk Painting; Traditional Toys; Other Handicrafts.

Buyer preference categories include: Sarees & Textiles; Pottery; Jewellery; Woodcraft; Metalcraft; Bamboo & Cane; Embroidery; Folk Art; Home Decor; Other Handicrafts.

Current seeded product data is primarily sarees, mundu, silk, cotton, Ikat, brocade, and handloom textiles. No seeded pottery, metalcraft, woodcraft, leathercraft, bamboo, toy, or painting product records were found in data.ts or the server seed.

7. Product Listing / Upload

The listing wizard is in WeaverView.tsx.

  1. Photo step: product photo upload/template selection is represented by selected photo state and sample images.
  2. Guided Q&A: title/what made, material, length/width, special features, and price. Questions and hints are defined in QA_QUESTIONS in data.ts.
  3. Input modes: microphone or keyboard typing; simulator fallback can provide demo speech.
  4. Review step: read/listen to summary, edit, or publish.
  5. Optional features: GI draft panel and AI fair-wage pricing review.
  6. Publish: constructs a Product, prepends it to React product state, resets wizard state, and speaks a success message.

The inspected publish handler does not directly call POST /api/products; server synchronization is available through offline outbox mechanisms and server endpoints.

8. Search and Recommendations

Search is a client-side conversational parser, not an external search engine. BuyerView.tsx filters products by status, saved state, color, maximum budget, material, occasion, and parsed query values.

Recommendations are not AI-generated. The current detail recommendation panel is deterministic and category-family based, using keyword matching over title, material, description, and GI category. It excludes unrelated families and displays a localized empty state when no matching products exist. The catalog itself remains mock/seeded and small.

10. GI Verification

GI data is represented by Product.giInfo and GiInfo. Fields include product name, registration number, origin, state/region, category, status, date, source, verifier, submission time, and notes.

Creation: the artisan wizard creates pending GI data inside the new product object. The server also implements PUT /api/products/:id/gi, which validates product name, registration number, and origin and sets status to PENDING. The current wizard does not directly call this endpoint.

Decision: AdminDashboard and GiModal call PUT /api/products/:id/gi/verify with VERIFIED or REJECTED. There is no separate clarification status or dedicated verifier workflow.

Storage: server product memory, React product state, and local product cache depending on the path. A real GI database is not connected.

11. Payment Protection / Escrow

Payment protection is a demo/sandbox escrow model stored in Order.paymentProtection. Seeded and newly created orders use a 20/40/40 milestone structure:

MilestoneShareMeaning
ORDER CONFIRMED20%Initial order confirmation/material advance.
CRAFTING / MAKING40%Craft completion/QC or logistics progression.
DELIVERED40%Final verified delivery.

POST /api/orders/:id/milestones/release updates the server order, milestone status, released amount, pending amount, transaction ID, and transaction history. Active disputes with status OPEN or UNDER REVIEW reject release. Client fallback can update local React state and generate TXN-LOC-... identifiers when the endpoint is unreachable.

This is not real payment processing. All transaction entries are marked demo/sandbox; no payment gateway, bank, or escrow provider is connected.

12. Buyer Disputes

Buyer disputes are raised in DisputeModal.tsx from the order view. The buyer supplies reason, detailed description, and an evidence URL/photo-notes text field. No binary photo upload was verified.

POST /api/orders/:id/disputes stores the dispute in the server-memory order with status OPEN. The client has a local fallback.

Artisans can respond through POST /api/orders/:id/disputes/respond, which sets the dispute to UNDER REVIEW. Admin can use POST /api/orders/:id/disputes/resolve for:

  • Request more information
  • Release remaining escrow to artisan
  • Full refund of pending escrow
  • Partial refund from pending escrow

Resolution updates dispute status, escrow amounts, milestone state in the release-payment path, and transaction history. Local fallback resolution is less complete than the server path and may not update every escrow/transaction field.

13. Admin

Admin is implemented in AdminDashboard.tsx. The UI has GI Verification, Disputes, and Transactions tabs. It can view seeded products with GI data, associated artisan and buyer information, disputed orders, escrow summaries, and transaction records.

Admin access is demo/client-side. LoginModal.tsx calls POST /api/auth/login, whose Admin branch recognizes a hardcoded demo identity. App.tsx also accepts ?role=admin and trusts stored profile role data. No session/token or backend authorization middleware is present.

Admin actions include GI verify/reject, dispute request-information, payment release, full refund, partial refund, and transaction refresh. Admin can switch internally to legacy Weaver or Buyer views and log out.

14. Verifier

A separate Verifier system is not implemented. No VerifierDashboard.tsx, verifier role, verifier API, verifier permissions, or verifier session was found. The word “Verifier” appears in labels and comments, including Admin-related wording, but it does not identify a separate executable workflow.

15. Voice Features

  • Speech recognition: VoiceHelper.tsx uses browser speech recognition where available, with simulator/manual fallback states.
  • Text-to-speech: attempts /api/tts using Google Translate TTS, then falls back to browser Web Speech API.
  • Languages: English, Kannada, Hindi; locale selection uses en-IN, kn-IN, and hi-IN where available.
  • Listing: Artisan Q&A can be voice guided and can use simulated transcript responses.
  • Buyer: voice search and artisan-story narration are present.
  • Offline: browser speech synthesis is used when offline or offline mode is selected.

16. Localization

Primary shared translations are in src/data.ts for English, Kannada, and Hindi. Onboarding has its own localized copy in OnboardingFlow.tsx. Pricing and payment tracker components include localized copy.

Localization is partial, not complete. Many public component strings remain hardcoded in English, including portions of BuyerView, WeaverView, AdminDashboard, DisputeModal, AccountModal, OfflineSimulationLab, OrderTrackingProgressBar, and LoginModal. Product names, descriptions, seed data, transaction descriptions, and some dynamic messages are not comprehensively translated. Complete Kannada/Hindi public UI coverage is therefore not verified / not implemented uniformly.

17. PWA / Offline

src/main.tsx registers public/service-worker.js, with public/sw.js forwarding to it. The service worker uses cache-first behavior for static assets/media and network-first with cache fallback for navigation/API requests.

Offline functionality includes:

  • localStorage product/order/profile caches
  • offline/data-saver simulation modes
  • outbox items for new products, QC submits, new orders, and status updates
  • server batch sync at POST /api/sync/batch
  • Last-Write-Wins timestamp comparison
  • conflict logs stored locally and server-side telemetry
  • background sync message forwarding

Limitations: the service worker precache list references source paths, not only production bundle assets; offline persistence is browser-local/process-local; server fallback data is not durable across restarts; and real multi-device conflict guarantees are not verified.

20. Security

  • Authentication: demo hardcoded auth; no session/token issuance.
  • Authorization: API routes do not verify caller identity or role.
  • Admin access: client accepts ?role=admin and stored role state.
  • Trusted fields: verification identity and several role-related fields are client-controlled.
  • Evidence: dispute evidence is a URL/text value; no upload/storage security was found.
  • Persistence: server memory is lost on restart; localStorage is user-editable.
  • Public admin UI: public GI modal includes an Admin Review Tool tab in the current component.
  • API exposure: GI verify, dispute resolve, milestone release, and transaction routes lack authentication middleware.

23. Current Limitations

  • No real database connection; server mutations are process-memory only.
  • No server sessions, tokens, or role authorization.
  • Admin mode can be activated through client URL/state handling.
  • No separate Verifier dashboard or role.
  • GI wizard data is local product data; direct GI submission endpoint use is not verified.
  • GI clarification workflow is not implemented as a dedicated action/status.
  • Evidence is a URL/text field, not a stored upload.
  • Checkout and UPI are simulations.
  • Escrow is sandbox/demo logic, not real custodial escrow.
  • Client fallback paths can diverge from server-side financial updates.
  • Localization remains incomplete; English strings remain in Kannada/Hindi experiences.
  • Catalog data is primarily handloom/textile seed data despite broader onboarding categories.
  • No multi-item cart was found; checkout is product-centric.
  • Product upload wizard does not directly call the product POST route.
  • Milestone sequencing is not fully enforced server-side.
  • Some public components expose Admin review language/tools.

24. What Can Be Shown in a Hackathon Demo

  1. Open the app and complete English/Kannada/Hindi onboarding.
  2. Select Producer/Creator or Buyer/Market Partner and demonstrate subtype-specific forms.
  3. Open Buyer marketplace, use conversational search, save an item, view product details and same-craft recommendations.
  4. Run direct checkout and show simulated UPI/order confirmation.
  5. Show order tracking and 20/40/40 payment protection with demo amounts.
  6. Raise a buyer dispute with description/evidence URL, then show active dispute freeze.
  7. Use the internal Admin route/login to show GI verification, dispute actions, and transaction ledger.
  8. Open Artisan listing wizard, use voice/simulator input, run AI fair pricing, add GI draft data, and publish a product locally.
  9. Open Offline Simulation Lab to demonstrate offline mode, outbox, and Last-Write-Wins conflict telemetry.

Demo claims should be framed as sandbox behavior. Do not present the current system as production payments, production authentication, durable database storage, or a separate Verifier platform.

25. Final Summary

TantuLink currently provides a polished, feature-rich marketplace demonstration with Buyer and Artisan-facing flows, dynamic onboarding, seeded product/order data, client-side search and recommendations, a deterministic fair-pricing service with fallback, GI status workflows, dispute and escrow simulations, voice features, PWA caching, and offline synchronization demonstrations.

The strongest implemented areas are the integrated UI flows, the shared order/payment/dispute data model, the server-memory endpoints for GI/disputes/milestones/transactions, and the offline outbox/LWW demonstration.

The system remains a demo architecture. The largest production gaps are real authentication/authorization, database persistence, real payment processing, a separate Verifier role if required, secure evidence uploads, complete localization, and consistent server/client transaction handling.

Audit conclusion: statements in this report are based on the current inspected source/configuration/data files. Any behavior not directly represented by those files is marked as not verified or not implemented.
